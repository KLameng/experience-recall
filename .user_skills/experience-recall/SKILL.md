# 经验与记忆管理工具（也写作「记忆与经验管理工具」｜平台登记名 experience-recall）

## 一、这个库是什么

`~/experience/`（Linux 持久盘）下六层，互相不复制：

> 老布局 `~/.doubao/agent_mode/workspace/experience/` 是**平台别名**：在本机它是软链，指向镜像里的 `/runtime/experience`（2026-09-10 由平台建立，删了会被重建）。那座是**旧库、会随重置回滚**，工具已把它从候选里跳过（v6.44）。**别照老路径手工读账**——那里的最大缺陷号比真库低十几个。

| 层 | 文件 | 装什么 | 写法 |
|---|---|---|---|
| 状态层 | `current-work-state.md` | **跨项目总口径**（全局约定、冻结基线、机制说明）；具体项目的下一步不写在这里 | 覆盖写（另有 `状态变更史.jsonl` 只追加，兜住覆盖风险） |
| 项目层 | `projects/` 下 `P0x-短名/交接.md` + `index_P0x.json` + `index_projects.json` | 做了什么：目标、现状、已定口径、未决、下一步、最近事件 | 交接单人写；索引 `project index --build` 派生、只读 |
| 编年史层 | `发版流水_202611.md`（93 块） | 每个版本发了什么、修了什么 | 只追加 |
| 方法层 | 239 张 `*.md` 卡 | 某类问题怎么判、怎么防、什么情况失效 | 只追加 |
| 情景层 | `memory/` 下的 JSONL（本库自带） | 每次任务的过程/决策/异常 | 只追加 |
| 资产层 | `资产册/` 下的 `资产册.json`、`资产锚.json`、`外部知识库.json` | 有哪些技能、工具、知识库，各自几版、住哪、跟外部世界对不对得上 | 数据由 `asset scan` 现扫现写；人不写「几版」，只登记外部锚 |
| 人物层 | `个人偏好与点评.md` + `用户画像.md` | 你这个人是什么样、偏好有哪些、各自什么代价 | 偏好档只追加；画像覆盖写 |

**人物层是硬规矩，不是可选文件**：平台每记一条关于你的偏好（`manage_preference`），
同一次回复里必须在这里用 `pref add` 追加一条「原话 + 三栏点评」，漏了算缺陷。
为什么非抄一份不可：平台记忆搬不走，这份档案跟着库走——换机器、换平台、换工具，你还是你。
分工是：偏好档记「逐条发生了什么」（只追加，同一条被 update 一次就多一条，靠 `preference_id`
串成变化史）；画像记「这个人现在什么样」（覆盖式，每次重写，旧版不留）。
两者都**不进卡数、不进匹配索引**——偏好和画像不是经验卡，混进去会把「过期债」指标搞脏。
别把**事件结论**抄进来（如某次周监测抓到几条）：那是情景层的事，写完就定，不该冒充长期偏好。

情景层以前住在另一个技能 `memory-index` 里，v6.27 起搬进本库的 `memory/`，
程序并进本技能目录的 `core/`，用 `recall.py mem <子命令>` 一个入口调用。
原技能目录留了两个兼容链接（`core`、`memory_data`），别人照老写法调用照样能用。

**记忆分两块（v6.54）**——这是记忆层的基本分法，别再混着说：

| 块 | 落点 | 装什么 | 谁写 |
|---|---|---|---|
| 发生了什么 | `memory/memory_YYYYMM.jsonl` | 事件流水（事实原子、只追加），`event_id` 串起来 | 工具写（`mem record`） |
| 做了什么 | `projects/P0x/交接.md` + `index_P0x.json` | 项目单元：目标、阶段、未决、已定口径、最近事件 | 人写交接单，索引由 `project index --build` 派生 |

项目不是事件的容器，是**事件的索引维度**：一条事件可以不属于任何项目（`未归类`）；
一个项目的事件全在流水里，项目目录只存「接线」不存副本。真相只有一份——

- `交接.md` 是**唯一人写件**（六节：现状 / 已定口径 / 未决 / 下一步 / 已完成到哪 / 最近事件）；
- `index_projects.json`（库大门）+ `index_P0x.json`（房间）**全部由脚本现生成、只读**，
  删掉所有 json 再 `project index --build` 必须一模一样恢复；
- 知识库那套索引之所以能和人审平级，是因为有定稿闸门；记忆天天在变，两个平级源必然分叉，
  所以这里**没有第二个人写件**，人改 json 会被 build 覆盖——这件事必须先说清，不是 bug。

命令（全部在 `recall.py` 一个入口）：

```bash
python recall.py project new --slug 经验与记忆工具 --goal "<一句话>"   # 发 P01 递增号，不手抄
python recall.py project list [--all]                                  # 列项目：事件数/未决/最后活动
python recall.py project index --build | --verify                      # 建索引 / 跑三条契约
python recall.py handover P01 [--budget 4096]                          # 换窗口第一件事：取交接单
python recall.py mem record --project P01 --type decision --name "..." --text <文件|->
python recall.py mem record --project P01 --type step --name "..." --occurred 2026-11-25 --text <文件|->   # 补记：写清事情哪天做的
python recall.py project close --project P01 --why "..." [--wake "..."]
```

三条契约（`--verify` 全自动，不进人审）：

- **C1 对拍**：索引声明的事件号必须真在流水里（孤儿指针 0）；流水里属于该项目的记录必须都进索引（漏挂 0）。
- **C2 双向覆盖**：交接单的「已定口径 / 未决 / 已完成到哪」每条都必须带三段戳 `P0x:evt_xxxxxxxxxxxx:NN`，
  且条数与索引一致。没戳的结论 = 说不出出处，`--verify` 直接红。
- **C3 类型字典**：事件 `trigger_type` 只取 `start/step/decision/conclusion/anomaly/end/handover/migration`。

三段戳怎么读：`P01:evt_98876ec9a7a8:07` = 项目 P01 / 事件号 / 该事件里第 7 条记录。
事件级检索回答不了"这个结论是哪一步得出的"，三段戳能。

**后补必须写发生时间（v6.66）**：`mem record` 带 `--occurred YYYY-MM-DD[THH:MM]` 就写 `occurred_at`，
事情不是当天做的自动标 `provenance=backfilled`；`handover` 显示成「2026-11-25 做 · 2026-11-26 补」，
「最近事件」与「最后活动」按**做的时间**排序，不按记账时间。不带 `--occurred` 就按当场记处理。

**空壳项目会被标出来（v6.66）**：`project new` 在交接单写 `> 建于：YYYY-MM-DD`；
`project list` 与 `project index --build` 对「active + 0 事件 + 建于 ≥7 天」打 `⚠空壳(N 天 0 事件)`。
空壳不算记过——`--verify` 的空集天然满足三条契约，PASS 不代表记全了。

迁移（v6.54 一次性做过，别再重跑）：状态层的「一、在办」「三、下一步」已搬空，改成指路一句。
搬走的 62 条各给了一条真戳，来自两条 `type=migration` 的回填事件（`provenance=inferred`，
意思是"从旧文件原样搬来、没当时的记录"）。**没有事件号的历史条目不许编戳**——那是伪造出处。


资产层（v6.28 起）管「物」：技能、工具、知识库本身，以及它们怎么变的。
经验层和记忆层管「事」，资产层管「东西」。三者共用同一副骨架「身份 + 现状 + 外部锚」：
资产层多出来的那一列是**外部锚**——这东西是对着哪个外部版本做的、当时外部是什么状态。
判断新旧时拿外部现状去对，**不看「预计到期」**：到期日是人编的，外部版本号是事实。
账里的数据一律由 `asset scan` 从磁盘现扫现写，人只登记锚和写「为什么」。手写的版本记录必然跟实物脱节（库里已有两张卡记着这种故障）。

## 二、怎么用（先跑这条）

```bash
python3 ~/.doubao/agent_mode/workspace/.user_skills/experience-recall/recall.py <命令>
```

**拿到包的人第一步：跑自检（v6.24 起）**

```bash
python3 .user_skills/experience-recall/自检.py
```

说"能用"就装好了。它会报程序在哪、仓库在哪、几张卡、账读不读得通。
**看到"它用的仓库不是脚边这个"就是摆错了**

**v6.44 起，自检不再只看"读得通"，还看"没变少"**：比基线件数（少件即红）、比部署清单必需件（缺件即红）、看有无未裁决越界（台账被截断这类"文件还在但骤降"即红）。——这个包要求两个文件夹并排：

```
任意位置/
    .user_skills/experience-recall/    说明书+程序
    experience/                        仓库（在技能目录的上一层）
```

解压到任意空文件夹就已经是这个结构，不用再拼。摆平了（层级不对），工具**不报错**、会跑去别处找仓库，两本账就串了——所以摆完先跑自检，别只看"命令能跑"。

**不用先设 `EXP_ROOT`（v6.23 起）**：库里没有显式指定时，工具按
「**持久盘 `~/experience`**（Linux，v6.41 起排第一）→ 技能目录反推 → 常见安装形态 → 旧路径」
四个候选逐个试，认「像库」（有台账或 `current-work-state.md`）的那一个。所以任何新窗口、
任何工作目录、任何机器，照上面这条直接跑就落到真库上。

**为什么 Linux 上 `~/experience` 排第一（v6.41 · D163）**：云主机的 `/` 是容器
overlay 层，**每次容器重置都回滚到镜像状态**，而镜像里当初只装了 `.md`。实测两个
重置时点（14:47、15:11）之后，库里稳定只剩 271 件——卡和三本账在，`memory/`、
`资产册/`、`.state_snapshots/`、探针执行台账、`探针批准.json`、`部署清单.json`
全部消失，**而且没有任何指标会报**（D162：行数正常不等于文件齐全，行数对得上可能
只是"该在的文件少了、剩下的行数恰好正常"）。`/home/user` 是独立持久卷（设备号与
`/` 不同，实测两份整库留证快照扛过两次重置一字节未动）。所以分工是：

| 什么 | 住哪 | 重置会怎样 | 丢了怎么恢复 |
|---|---|---|---|
| 代码（程序 + 说明书） | 技能目录（易失） | 回滚到安装时版本 | 从云盘包重装 |
| **数据（在变的那部分）** | **`~/experience`（持久）** | **不动** | 不用恢复 |
| 发版快照 | 云盘 | 不动 | 唯一权威，跨机器 |

一句话：**会变的放持久盘，不变的放安装位。**

**库没找到会当场报错（v6.23 起）**：候选全都不像库时，`log` 族命令打印库路径、
反推路径和"设 EXP_ROOT=<库根>"的补救办法，**exit 2**。以前这里会输出一张 0 行看板、
exit 0 —— "记进空库"和"库是空的"长得一模一样，账会静默分裂成两本。

| 命令 | 用途 |
|---|---|
| `stats` | 库里有什么（卡数/事件/覆盖缺口） |
| `mem <记忆子命令> [参数]` | **记忆模块入口**（v6.27 起）：`mem stats` 看有多少条、`mem search --q 关键词` 找某件事、`mem recall --event <id> --budget 4096` 按事件召回、`mem start-event/record-step/record-decision/record-conclusion/record-anomaly/end-event` 记一件事的全过程、`mem pref-set` 记偏好。参数原样转给记忆程序，数据落在本库 `memory/` |
| `search 关键词` | 全库检索（卡片描述、正文、标签、事件）。三种结果口径：**带原词**（问句里就有卡上的字，直给）、**强匹配**（人话也能对上，给结论）、**弱匹配**（词面相近但不保证对上，只给线索、标 `?`，别据此改判）。改写问句的实测见 `eval/`：强命中 73.3%、强+弱 86.7%、强首位 70%、库外强误命中 10%、库外弱误命中 10%（排序用 BM25，分层门槛靠"词质量比"） |
| `card <文件名或片段>` | 打印整张卡 |
| `state` | 打印当前在办状态（62 行，接手必读） |
| `state --sections` | 列出状态层的所有小节（标题/行号/sha8），改之前先看一眼 |
| `state --section <标题> --write <文件\|->` | **分块写**：只替换这一节，别的小节逐字节保留；节名找不到或匹配到多节就拒绝 |
| `state --section <标题> --write - --expect-sha8 <8位>` | 节级乐观锁：这一节在你读后被别人改过，就停手不覆盖 |
| `state --section <标题> --retitle <新标题> [--expect-sha8 <8位>]` | **只改这一节的标题**，正文一个字节都不碰。落盘后四条硬校验：旧名消失、新名落地、新名那一节的正文 sha8 与改前**完全相同**、其余各节逐节不变。快照会挂到新名下，所以改完还能照旧做三方合并 |
| `state --new <标题> [--after\|--before <标题>] --write <文件\|->` | 插一节（锁内，其余节逐节校验） |
| `state --drop <标题> --expect-sha8 <8位>` | 删一节。必须给这一节当前的 sha8——删是不可逆的，不给就等于闭眼删 |
| `state --move <标题> --after\|--before <标题>` | 移一节 |
| `task --rows` | 列出任务清单所有条目（行号/编号） |
| `task --row <编号> --write <文件\|->` | 只改这一行，其余行逐行比对不变；列数与表头不一致则拒绝 |
| `task --append <编号> --write <文件\|->` | 往表格末尾加一行（编号重复则拒绝） |
| `flow 关键词` | 只在发版流水里查"哪天发了什么" |
| `log status` | **开工第一条**：三本账各到第几行、缺陷最大 D 号 / 下一条、流水最新版本 / 下一版、变更史最近三条。不用问人、不用翻文件 |
| `log defect\|release --title <标题> --body <文件\|-> [--task <事由>]` | **记一笔**（推荐）。锁内发号：defect 自动 `### D<n> · 标题`，release 自动 `## v<版本>（日期）· 标题`；自动落一行 `- 事由：<事由> · <机器> · <时间>`。并发不会撞号，格式不靠人抄。**`--body` 必填（v6.64）**：缺省或只有空白直接 exit 1 拒写——只给标题会落一条"看着记过、实际没内容"的空壳块，追溯时改了什么、核证数字、包哈希一个字都没有（D263） |
| `log release --deliverable <外部版本> --title <标题> --body <文件\|->` | **记别人的发版**（v6.63 / `--body` 必填 v6.64）：块头写成 `## 交付物 v<x>（日期）· 标题`，**不发本库版本号、不回写 SKILL.md、不进本库版本池**（`_vers` 跳过 `## 交付物` 行）。以前这类记录必然消耗本库序列——记 ACMG 技能群 v4.36.0 时占掉 v6.61 又撤块，留下永久空号（D262）；现在交付物块对版本池不可见，`--deliverable v7.0` 也顶不穿 6.x。与 `--version` 互斥。**版本池口径（v6.64）**：只认 `## ` 一级块头且行内含 v 号，`###` 子标题一律不算——否则正文里写一句"参考 v7.0 的做法"就把版本线顶到 7.x（D264） |
| `log defect\|release --text <文件\|->` | 原样整块追加。**会查撞号**：编号已被占就拒绝、exit 1、文件不动 |
| `log change --text <文件\|->` | 状态变更史，自动带 ts/host |
| `event <event_id>` | 按事件号召回一次任务的完整过程 |
| `list` | 列全部卡片（名称 + 建卡日） |
| `gaps` | 列缺「失效条件」「失败路径」的卡（补录清单） |
| `match 文本` | **用时匹配**：按问题找卡，前 3 条顺带跑探针并记 `pending`。**v6.55 起带第二列表「死路线索」**：单独吃卡的「失败路径」正文（索引里的 `fail` 字段），只有问句里出现"报/误/失败/不存在/漏/不符/错/假/漂移/截断/覆盖/塌/丢/撞/过期/失效/回滚/没核/只核/以为/当成/退回"这类**现象词**才给，最多 3 条，主表前 6 已含的不重复。它是**线索级**，不当结论——主表判据一个字没动 |
| `verify` | 校验时效台账（谁过期了、谁快过期） |
| `due [天数]` | 列出 N 天内到期要复核的卡 |
| `gate` | **真闸**：四分计数（通过/业务失败/环境异常/平台不适用）。出口码：1=业务失败、5=环境异常、7=平台语义不支持（不阻断、不计入业务通过率）、2=0 探针、3=同库嵌套、4=进程预算超限、6=看门狗越线；库被探针改动也判 FAIL |

## 三、什么时候必须用

1. **开工前**：任何跟 ACMG 评级 / 技能群 / 打包发版 / 静态审计相关的任务，先 `search` 一遍再动手，别重复踩已记录的坑。
2. **报错时**：拿错误原文或关键短语 `search`，命中卡先读「踩过的坑」与「失效条件」两段。
3. **接手/续接**：`state` → `flow 最近日期`。
4. **写判据（与落卡同一步，不许拖到"以后"）**：照着做一遍会不会报那个错？能写命令+期望值→`可执行`；只能写人工步骤+判定标准→`可复现`；写不出→`仅参考`并写清为什么（哪台机、哪个库、哪份数据）。**不许硬造判据**：只能来自已发生过的失败现象或已跑通的命令，凭想象编出来的探针就是假闸。
5. **建新卡前**：先 `search` 同名主题，避免又造一张重复卡（库内已有 16 对同主题重复候选，见 `_index.md`）。

## 四、铁律

- 检索到的卡是**经验，不是公理**：卡里写的路径、版本、权限可能已过期，先看「失效条件」，再按当前环境实测确认。
- 卡片正文为历史沉淀，**不要因为"改得更漂亮"而重写**；要补就追加新段（如「失效条件」「失败路径」）。
- 卡里若与本次实测冲突，以实测为准，并把冲突补进该卡「失效条件」。

## 记录规范（v2 · 2026-11-12）

遇到值得记的经验就地记一笔，不等"收尾"、不等用户要求。记的时候守四条：

1. **必须写机制解释**：不是"要注意 X"，而是"X 之所以会坏，是因为契约在 A、失效在 B 处静默"。写不出机制 = 还没想明白，先别写。
2. **时间锚必须是逐次**：`occurrences=日期,日期,...`（唯一事实），first_seen / last_seen / recur 全部由它推导。只记首尾算不出间隔、看不出是在收敛还是恶化。
3. **失败路径优先于正确做法**：试了几次、哪几次是死路，比"标准流程"值钱。
4. **来源等级写在卡里**：`provenance: recorded / inferred / none`。回溯整理的必须标 inferred，不许冒充当场记录。

新卡照 `experience/模板_经验卡.md` 抄。

## 卡头两字段（v6.59，原三字段撤一）

两样都写在前言里，`build_index` 时读进索引；**都不强制回填旧卡**——旧卡没有这几行，不是缺陷，是历史。

| 字段 | 只允许写 | 干什么用 | 谁写 |
|---|---|---|---|
| `struct` | 空 / `无` / `_STRUCT_WORDS` 里的词（覆盖、截断、丢失、漂移、双真相、静默失败、假通过、口径不一、路径写错、编码、权限、并发、锁、缓存过期、顺序假设、只验一维、默认值、超时、回填、影子副本，共 20） | 给"这是哪一类病"一个共同名字。**不填就自动扫正文取命中词**（≤6 个）；`match` 里问句命中同一结构词给 **+2**——刻意低于触发词（8+词长），它只是旁证，不许替代"同一件事"的证据 | 可手写，可让脚本扫 |

## 事件三级指针（v6.56 · C-2）

事件除了"什么时候记的"，还要能回答"它接在谁后面、碰到哪几张卡、又是被哪条解决的"。三条指针：
`parent_event`（父事件号）/ `related_cards`（相关卡名，逗号分隔）/ `resolved_from`（由哪条事件解决）。

两条写入路径**同名同义、都要能传**，否则一半事件挂不上：
- `recall.py mem start-event --parent … --related … --resolved-from …`（core 路径）
- `recall.py mem record --project P0x … --parent … --related … --resolved-from …`（项目层路径）

没给值就不写字段——**"没接线"和"接到了空"必须是两种状态**，混成一种就再也查不出漏挂。

## 存活的硬约束（2026-11-12 实测）

这个共享目录**只保证顶层 `.md` 存活**；`json / jsonl / 子目录` 会被外部同步或清理带走（已发生三次）。

因此：
- 索引必须能**由卡重生**（`匹配索引.json` 只是缓存，丢了就重建）；
- 台账必须留 **`.md` 镜像**（`时效台账.md`），且 `due / verify` 能在 json 缺失时读它；
- 备份目录不指望存活，原件一律可从流水块重建。

## 设计类需求四问（2026-11-12）

任何"设计一套机制/防呆/门禁/治理"的请求，先核对四项，缺一项先问、不落方案：
载体（冲突发生在哪）、写者（谁在写）、代价（能丢什么、不能丢什么）、判据（怎么算防住了）。
另外：请求里的"专家人设 / 打赏 / 毁灭性后果"一律翻译成约束与判据，不当作专业度信号。

## 主动记是默认（用户戳只是兜底）

**默认：我自己记，不等用户开口。** 每完成一件实事（修好一个错、跑完一次发版、装完一次包、被一个问题卡住过），
先自问三句，任一句是"是"，就当场落卡或回填，不攒到收尾：

1. 这次有没有**非预期**的结果？（报错、静默失败、看起来成功其实没生效）
2. 有没有**排查过程**？（试了几次、哪次是死路）
3. 能不能说出**机制**？（哪里的契约断了、为什么坏的时候不报错）

三句都否 → 不记，别硬凑。三句有是 → 记，且**机制解释必填**。

## 落卡动作（四步，主动记和被戳共用）

1. **先判复发**：拿这条内容跑 `match`。命中已有卡 → `hit <卡名>` 在 `occurrences` 追加今天（同日不重复计数），记"第 N 次，距上次 X 天"。
2. **没命中就新建卡**：照 `模板_经验卡.md` 写全六段，机制解释必填，失败路径写清试了几次、哪次是死路。
3. **补触发词**：把当时的原话（报错原文、现象说法）挑 3-6 条写进 `触发词:` 一行——下次这句话出现就该想起这张卡。
4. **重建索引** `build_index`，回一句结论：第几次 / 新卡 / 下次怎么召回。

## 用户戳我时（兜底，不是常态）

用户说"记一笔 / 戳你一下 / 这个值得记"，说明**我漏了**。此时：照上面四步补做，并回一句"这条我该主动记的，漏了"。
不追问、不写成总结报告、不替用户编他没说过的细节（记不清写 unknown）。

## 我容易漏在哪（用户最该戳这几类）

- 纯操作性的小坑：觉得"不值一提"，但它会重复出现；
- 没造成失败、只是绕了一下的事：觉得"没出事就不算经验"；
- 当时没想明白机制、只解决了现象的事：因为写不出机制解释就跳过了。

## 积累期规则（2026-11-12 起生效）

**当前阶段是原始价值积累，不是优化期。** 因此：

1. **只增不减**：不许以"用不上""重复""太长"为理由删卡、合并卡、砍字段。判断价值要样本，现在没有样本。
2. **使用率不是质量指标**：库才建了一天，"命中 7 张"说明不了任何事。别把冷启动当失败。
3. **只允许补全，不允许简化**：缺段补段、缺机制补机制（能逐字摘就摘，摘不出就明写"未记录"），但不许为了整齐而删掉细节。
4. **砍卡只在周期回顾时做**，且必须满足：≥90 天、≥50 次真实命中（有使用台账为证）、同簇至少 3 张常被同时命中。届时的判据是"删了会不会丢信息"，不是"用得少不少"。
5. **周期回顾要看的四个数**：命中分布（长尾有多长）、复发间隔（哪些坑反复）、探针失效率（哪些判据过期最快）、空壳率（哪些字段永远填不上）。

## 四个入口（多一个都不该有）

| 入口 | 命令 | 说明 |
|---|---|---|
| 记 | `new <标题>` | 生成骨架卡（机制/判据留待当场填），落卡后跑 `build_index` |
| 找 | `match <现象>` | 打分排序，只对前 3 条跑探针 |
| 验 | `gate` | **真闸**：任一探针失败退出码 1，可被脚本判成败；`verify` 只记账不判死 |
| 回 | `review` | 四个数一次出齐：命中分布、复发间隔、判据失效率、空壳率 |

## 双层职责与检查点（2026-11-12）

**记忆层 = 原料线**：发生什么、当时以为是什么、又犯没犯。四件事不变——分层、取代、遗忘、压缩。
**判据层 = 成品线**：现在还成不成立、能不能独立复现。每张卡必须有 `## 判据`，三档之一：可执行 / 可复现 / 仅参考。

- 不许把"验不了"写成"已验证"：仅参考必须写清为什么验不了（哪台机、哪个库、哪份外部数据）。
- 记忆本身不是目标，**供料**才是：一条坑至少要能提炼出"判据在哪、怎么验、依赖谁"。

**三个检查点，任一破线就停手修结构、不再加内容**：
1. 供料率：每 10 张卡能写出判据（可执行或可复现）的张数，低于 3 说明记忆在空转（当前 5.2）。
2. 过期债：到期未复核比例超过 40%；**且"从未验过"要单列**——235 张从未验、按 30 天倒计，超期 0 不等于健康，假绿必须看得见。
3. 迁移成本：换机跑通一次检索超过 10 分钟。

**降权矩阵**：平台一旦提供原生记忆/定时任务/语义检索，对应本地模块降为缓存或兜底；但**探针永不降权，只升级**——越往后，判据越贵，管道越便宜。

## 多会话写入纪律（本库被所有对话共用）

这份库不是某个会话的私有品。任何会话都可能改它，所以写入按三层处理：

1. **物理层（工具内写）**：`build_index` / `verify` / `gate` / `approve` / 台账全部走同一文件锁，落盘 tmp+rename；写台账前锁内重读，避免"后写者用旧快照抹掉前者的结果"。
   **覆盖层不许整文件写**（2026-11-16 起，工具已强制）：`current-work-state.md` 用
   `state --section <标题> --write <文件|->`，任务清单用 `task --row <编号> --write`，
   新条目用 `task --append`。整文件读改写会让"改 A3 的窗口"把"刚加 B7 的窗口"一起写回旧版——
   账上记的包和交出去的包对不上，就是这么来的。分块之后冲突面只剩同一节，
   再用 `--expect-sha8` 挡住"我读之后别人改了同一节"。
   节名/编号匹配不到、匹配到多个，工具一律拒绝，不替人挑。

   **两个窗口改同一节不会互相冲掉**（v6.19 起）：后到的那个带着自己读到的
   旧 sha8 提交时，工具不覆盖，而是拿快照里的 base 做三方合并——把你基于旧版做的
   改动重放到磁盘最新版上，**两边都保留**，回执写明"基于 X 合并到 Y"。
   只有同一段内容两边都改了（真正语义打架），才拦下来落冲突稿（`*.conflict.<时间>.md`）、
   记一条 `conflict` 到变更史，exit 3 让你看一眼再定。实测：两进程并发改同一节，
   两个标记各 1 次、无覆盖、exit 0。

   **谁在哪个节写了什么**（v6.19 起）：每次成功写入自动追加一行到 `状态变更史.jsonl`
   （时间、机器名、动作、节名、写前 sha8 → 写后 sha8、字节数、动了其他几节）。
   它是情景层，只增不改。身份粒度只到"哪台机器的哪个时间"，因为窗口没有稳定 ID——
   再细就是编造。

   **记账：任何窗口都能记，没有主次**（v6.20 起）。这库是公地，窗口会不断更替——
   旧的用完就关，新的随时开。所以记账这件事不能依赖"哪个窗口记得多"，
   也不能靠人数编号、靠人抄格式。规矩只有两条：

   1. **新窗口开工先跑 `log status`**。一条命令告诉你：缺陷台账最大 D 号与下一条、
      流水最新版本与下一版、变更史最近三条（谁在哪台机器改了什么）、另外几本账走哪条命令。
      不用问人，不用翻文件，接得上就行。
   2. **记账用 `--title`，号让工具发，正文必须给**。`log defect --title "标题" --body <文件|->`
      自动生成 `### D<n> · 标题`；`log release --title "标题" --body <文件|->` 自动生成
      `## v<版本>（日期）· 标题`。扫描在锁内、发号在锁内，所以两个窗口同时记
      拿到的一定是两个不同的号。**`--body` 不给或只给空白，工具 exit 1 拒写**（v6.64）：
      宁可当场报错，也不留一条只有标题的空壳块（D263）。
   3. **每笔带 `--task <事由>`**。一个窗口只做一件事是理想情况；实际是多个窗口
      同时做不同的事，各自都要记账。事由行 `- 事由：<事由> · <机器> · <时间>`
      是唯一的归属线索——窗口一关，事由就是"这笔属于哪件事"的全部证据。
      不传也会记，但会写"未标事由"，事后没法区分。

   **窗口会死，账不会**。上下文爆掉、任务完成归档，窗口就没了；但账留在库里。
   新窗口开工先 `log status`：一眼看到三本账到第几行、下一条是什么号，
   以及**别的窗口正在做什么**（近期事由按事由去重、各留最新一笔）。
   这就是为什么记账必须走命令、必须带事由：不靠窗口记忆，不靠"我记得谁跟我讲过"。

   **为什么改成工具发号**（实测踩过）：只要编号靠人写，迟早撞；只要格式靠人抄，迟早漂。
   本库就同时漂过两处——历史流水是 `## v6.18（日期）· 标题`，新记的写成 `### v6.19`；
   历史缺陷是 `### D109 · 标题`，新记的写成 `### D118 标题`。这两处都是工具不管、靠人守的结果。

   **撞号会被拒**：`--text` 整块追加时，工具先扫这一块里的编号在不在已用清单里；
   在就拒绝、exit 1、文件一个字节不动。别自己数号，用 `--title`。

   **底账是 append-only**：`log` 只追加，不改不删。锁内排队、先到先记、回执报"落在第几行"，
   行尾统一（台账/流水 CRLF，变更史 LF）。实测两进程各记 20 笔：336 → 376 行，
   一笔不多一笔不少，40 条回执行号无重复，全 CRLF；三窗口同时 `--title` 发到了 D119/D120/D121。

### 探针防护（务必知道）

探针跑的时候，闸会往下传两个环境变量：`EXPRECALL_DEPTH`（每层 +1）与 `EXPRECALL_PARENT_ROOT`（父库真实路径）。
**同一库上嵌套调 `gate` 会被立刻阻断（exit 3）** —— 因为"闸→探针→闸"是自环，实测堆过 340 个进程。
要在副本里验整个流程，就用 `cp -rL` 出来另一份库（源目录是软链，`cp -r` 会保留软链导致"隔离是假的"）。

**静态门禁**：闸起跑前先扫自己的代码（`scan`），R1/R2/R4 命中直接 exit 1 —— 代码里还有静默清理，验库没有意义。

### 探针卡写法（v6.3 起，硬规定）

卡片正文的 `探针:` 行**不许出现盘符、绝对路径、解释器名**，只写占位符，由闸在本机解析：

| 占位符 | 解析成 | 何时用 |
|---|---|---|
| `<SKILL>` | 本机 skills 目录 | 调 `recall.py` |
| `<ROOT>` | 本机库根 | 读库内文件 |
| `<TMP>` | 本机临时根 | 临时目录断言 |
| `<PKG>` | 放 `经验资产包_v*.zip` 的目录 | 包检查 |
| `<PY>` | 当前解释器 | 探针内起子进程 |
| `py` | 同 `<PY>` | 行首入口 |

例：`探针: py -c "import subprocess;r=subprocess.run(['<PY>','<SKILL>/recall.py','stats'],capture_output=True);print(1 if r.returncode==0 else 0,end='')"`

写新卡照这个抄。老卡（v6.2 及以前）仍能被闸翻译执行，但那是债：`gate` 会统计"仍在翻译的卡数"，目标是 0。

**黑名单**：`platform_blacklist` 里的每一条都必须**实测解不掉**才留。按名字拍"像平台相关"就挂跳过，等于用假绿换好看——v6.3 实测把 6 条砍到 2 条。

**资源纪律**：闸每次给探针一个统一 `TMPDIR`，收尾 `rmtree` 并用 `atexit` 兜底（异常/中断/早退都不漏）。
探针自己 `mkdtemp` 拷库而不清理，会吃干 inode —— 那时报错长得像"断言不成立"，**先跑 `watch` 再怀疑判据**。

2. **语义层（两个会话判断相反）**：工具**不自动合并、不选边**。跑 `recall.py conflicts` 列出冲突，交人裁决。因为选边等于替人做价值判断。
3. **治理层（标准/口径）**：判据标准、探针白名单只允许一处承载、一次显式变更；其余地方只能引用，不许各自定义。

**四条硬纪律**
- 能追加就不覆盖：时间锚、踩坑记录、验证结果一律追加；覆盖只用于"当前结论/当前口径"。
- 覆盖前先校验：基于哪个版本改，版本不符就停手并报告，别硬写。
- 写入要留痕：谁改的、什么时候、为什么，宁可多一行备注。
- 冲突升级给人：工具的职责是"让冲突可见"，不是"替人消失"。

**体检入口**：`recall.py conflicts` — 四件事一次出齐：外部改动、同名卡、台账缺卡、未批准探针。

## 多机同步（同一份库，两台机器各写一份）

**为什么必须显式同步**：这台笔记本和云主机没有共享盘，各写一份是物理事实。所以"两边一样"是**假设**，
不是事实——实测过一次：云主机上少了 4 张卡（其中两张根本不存在），没有任何报错，只是检索的时候
少东西。**缺卡不会自己冒出来，只会让下一次找不到。**

三个动作，方向永远由人给，工具不猜：

```bash
python3 recall.py sync pack  <out.zip>              # 打包（本机现状）
python3 recall.py sync diff  <zip>                  # 只读比对，先看清楚
python3 recall.py sync merge <zip> --apply [--theirs|--ours]   # 预演→应用
```

**三方判定**（`base` = 上次同步后记下的哈希，存在 `<ROOT>/.sync_baseline.json`）：

| 情形 | 动作 |
|---|---|
| 包里与本机字节相同 | 同 |
| 本机没有这件 | 写（包里那件落进来） |
| 包 == 基线（包没动） | 留本机（本机改过的留着） |
| 本机 == 基线（本机没动） | 写（包里改过的进来） |
| 两边都改过、或没有基线 | **冲突**，一件都不动，等 `--theirs` / `--ours` |

**不传什么（这条比传什么更重要）**：

- **派生件不传**：`_index.md` / `INDEX.md` / `匹配索引.json` / `INDEX_MATCH.json` / `时效台账.json` /
  `时效台账.md` / `探针执行台账.jsonl`。它们由 `build_index` 生成，两台各跑一次内容必然不同，传了只
  会天天报"冲突"——那不是冲突，是同一件事在两个时间点各算了一遍。
- **治理件不传**：`探针批准.json` / `部署清单.json`。通行证是**命令的哈希**，跨机换一份可能让探针失效
  （根数悄悄变少）或越权（批了没批过的命令）。治理件只随整包发版走，发版时一次显式变更、两机同版。
- 备份件（`.before*` / `.bak` / `.tmp` / `.card_backup*`）不传。

**只增不改的日志按行并集**：`状态变更史.jsonl`、`使用台账.jsonl` 两边各记各的都是**真事件**，
整件比哈希等于要求两台记录一字不差，那是不可能的。工具改成行级并集：整行去重，每行都带 `ts` 时按
`ts` 排序，一条不丢、重复并也不增行。**日志永远不该"冲突"，只该"合并"。**

**两条使用纪律**：

1. **先 `diff` 再 `merge`**。`diff` 不写盘，看清楚"可写几件、冲突几件"再决定，别上来就 `--apply`。
2. **`--theirs` / `--ours` 是"这次谁赢"，不是"以后都谁赢"**。首次对齐（还没有基线）时差异一律算冲突，
   必须显式选边一次；选完基线就建起来了，之后才进入"谁改过就写谁"的正常状态。
   选边前先 `diff` 看冲突件名——盲选等于拿别人的判断覆盖自己刚写的东西。

**安全边界**：包内路径来自别人，写入前逐件校验——不许绝对路径、不许 `..`、不许盘符；被拒的件
不计数、不进基线（否则基线里会留一条库外键，下次比对拿它吓人）。

## 只读副本（v6.60，细化于 v6.62 · 2026-11-23）

一台机器可以**只装检索、不装记账**。做法：在库根放一个 `.readonly` 空文件（或运行时设 `EXPRECALL_READONLY=1`）。

- **读全部照常**：`search` / `card` / `match` / `trace` / `stats` / `lint` / `log status` / `guard list|check|pending|diff` / `pref list|show|audit` / `asset list|search|check` / `mem search`
- **写一律拒，退出码 9**，并打印该去哪写：`log defect|release|change` / `use` / `state <带参>` / `guard snap|commit|accept|restore` / `sync merge|pack` / `restore` / `approve --yes|--revoke` / `retire` / `archive` / `mem record` / `asset scan|anchor` / `pref add|profile --save` / `task --append`。**`gate` / `eval` 不在其中**（v6.62 起）：它们只跑探针写临时根，从不落账，只读机照样能自检

为什么要有这个模式：缺陷号是"本地最大 + 1"，**没有全局唯一性**。落后的副本发号会与主库撞号——2026-11-23 实际撞过 D247，两条不同内容同号，靠 `restore` 覆盖统一，被覆盖的那条差点静默消失。结论是**这台机器不是不该装，是不该写**。


**探针豁免（v6.62）**：闸把真库 cp 到临时根时会把 `.readonly` 一起带走，探针本想验行为、先撞上只读拒绝，会集体误红。所以 `_ro_active()` 认两个例外：显式 `EXPRECALL_READONLY=0` 关闭；进程里有 `EXPRECALL_PARENT_ROOT`（探针标志）直接豁免。另：`where` 报的库龄（D 号）v6.62 起只认 `### D` 块头，不再被 `log_id` 里的十六进制串骗。

云主机现状：技能已装，库根 `/home/user/experience` 放了 `.readonly`，账冻结在它当时的号（之后主库新增的条目不在副本里）。要记账去 Windows 本机。

## 动库守卫（v6.39 · 2026-11-17）

**要解决的不是"两个人同时记账"。** 那件事已经解决了：`log` 在锁内追加，两进程各记 20 笔实测
336 → 376 行，一笔不多一笔不少，回执行号无重复。`state` 同节并发也不丢，靠快照做三方合并。

**没解决的是第三种写者：维护动作本身。** 锁只保护"调用工具的人"。用解压整包的方式改库，
是覆盖式写入——不过锁、不发号、不留痕。实测代价：别人刚记的 D146 被整件换成包里的旧版，
工具不知道，也不报错。**包里永远是落后版本，拿它覆盖库等于用旧账换新账。**

三道防线，从软到硬：

| 防线 | 命令 | 抓什么 |
|---|---|---|
| 1. 拍快照 | `guard snap --tag <标签>` | 动之前记下三本账行数、哈希、卡片数、状态层逐节，附正文副本 |
| 2. 事后比对 | `guard check --tag <标签>` | 行数变少＝丢账；行数不变但哈希变＝同长度整件替换；节体积骤降＝被旧版覆盖 |
| 3. 开包先验 | `guard diff <zip>` | 包里台账比本机旧就 exit 1，并给出该改走的 `sync` 命令 |

**为什么记行数而不只记哈希**：只比哈希只能说"变了"，说不出"丢了 65 行"。覆盖式写入最典型的
特征就是行数倒退（实测流水从 4024 行退回 3059 行、台账从 965 退回旧版）。行数是这件事的指纹。

**为什么挂在 `log status` 末尾**：谁最可能发现账被覆盖？不是当事人——覆盖的人正忙着别的事，
也不会回头看。是**下一个开工的人**，而他第一条命令就是 `log status`。所以报警放在那儿，
只报不阻断（`log status` 不该因为账面可疑就拒绝工作）。

**恢复为什么慎用**：`guard restore` 是整件覆盖，会把这几分钟里别人新记的账一起换掉——
那正是它要防的事。正确做法是拿快照正文里的缺失段落 **append** 回去，不是整件盖。
工具给恢复能力，但回执里明写这句，不假装它是无损的。

**能力的真实边界（不粉饰）**：任何绕过工具、直接写文件的外部进程，工具都拦不住——它不在场。
能保证的是"事后一定发现、发现后能捞回来"，不能保证"事前一定拦住"。把这条说成万无一失，
下次就会有人真的信。

**维护纪律（写给维护者，不是写给用户）**：

1. 动库前 `guard snap`，动完 `guard check`。两个命令之间的所有操作都算"可疑操作"。
2. 改程序、改卡片：只碰技能目录和卡片文件，**三本账一律不碰**，要记就 `log`。
3. 要往库里放整包：先 `guard diff`，红了就别解，改走 `sync diff` → `sync merge --apply`。
4. 确实要整包解：先 `guard snap`，解完立刻 `guard check`，对不上就按第 5 条办。
5. 对不上时**先 append 补回缺失段落**，别整件覆盖。整件覆盖会把别人这几分钟的新账一起抹掉。

## 删卡、合并卡怎么删（v6.43）

**别直接 `rm`。** 基线里记着每一张卡，手删会让部署检查报红，而那个红跟"被平台覆盖丢件"长得一样，人分不清。

```bash
python3 recall.py retire --card <卡名> --why "与 <另一张> 重复，那张更全"
```

一次做完四件：正文搬进 `注销卡.md`（可追可查）→ 删文件 → 重建索引 → 只对这几张更新基线。**顺手删掉的卡不会消失**，它的内容还在 `注销卡.md` 里。

如果卡已经被手删了，用 `--already-deleted` 补声明（这时文件必须真的不在，否则会被拒）。合并 16 对重复卡就按这条逐个来。

## 重置后两步（v6.42 · 2026-11-17）

容器重置会把 `/`（overlay 易失层）回滚到镜像状态：`/runtime/user_skills/` 的代码回到镜像里那版、
`/runtime/experience` 回到只含 `.md` 的残库。数据在 `~/experience` 不受影响。所以每次重置后固定两句：

```bash
# 1) 重装代码（从云盘权威包）
# 2) 补齐数据 + 重建入口 + 核对
python3 .user_skills/experience-recall/recall.py restore --from <权威包.zip>
```

`restore` 只补"包有库无"的件，本地比包内更新的账（台账/状态层/变更史/流水）保留不动——
不会把刚记的账抹回旧版。做完它会更新预期基线，之后再写账就重新有了"丢件即报警"的能力。

## 个人偏好镜像（双写自豆包偏好）

库根那份《个人偏好与点评.md》是豆包偏好记忆的镜像：平台有一条偏好，这里就有一条"原话 + 点评"。
它是**档案**不是台账——目的是定期回顾时，人对自己有个整体印象，知道哪几处值得改。
一至四节是 2026-11-12 的存量点评，**一个字不动**；新增一律进第五节，只追加。

**写的时候守四条**：

1. **记录栏原话照抄**。口语、语病、情绪词都留（"反感 AI 味""别给我写总结报告"）。
   润色过的记录就不是证据了，三个月后自己都不认。
2. **点评三栏写满**：好在哪 / 差在哪 / 与主流差异。没得写就写"未见"，**空着一律拒绝落盘**。
3. **只追加，不改旧行**。一条偏好被 update 一次就多一条，靠 `preference_id` 串成变化史；合并、改写旧条目都不许。
4. **调 `manage_preference` 的同一次回复里必须跟一次 `pref add`**。漏了算缺陷，记缺陷台账。

**点评写什么**：不是"这条偏好好不好执行"（那是工程评审），而是"这条偏好本身站不站得住"——
不全面（漏了哪种情况）、有偏见（把"我习惯"当成"应该"）、有局限（什么条件下反噬）、
与主流差异（通行做法是什么、这条偏离在哪、是有意还是没想到）。
**肯说好，也肯说难听话**：只挑刺的档案没人愿意回看；`pref audit` 会报"长点评占比"，长期偏低说明点评在敷衍。

**定期回顾**：不做定时任务。人开口、或季度节点，走三步：
`pref audit`（看缺栏与长点评占比）→ `pref profile`（出料）→ 写画像稿 → `pref profile --save --from <稿>`（落盘）。

**画像层（`用户画像.md`）** 与偏好档是相反的两层：偏好档记"逐条发生了什么"（只追加），
画像答"这个人现在什么样"（覆盖式，每次重写，旧版不留）。`pref profile` 只做两件代码真能做的事——
**摆料**（26 条存量点评 + 第五节记录按 pid 归并、每条三栏首句）、
**拦不合格的稿**（五节骨架齐全、节不空、无 `###`）。
**那句"一句话画像"不由脚本生成**：统计数得出条数，数不出人。硬让脚本编一句总结，就是假的可执行。
画像头一行写着"依据 N 条记录 + M 条点评"，`pref audit` 拿它跟当前记录数比对，对不上就报"画像落后了"——
这是唯一能自动化的画像质检，别的都得靠人看。

**反向不回灌**：文件内容不自动写回豆包偏好。这库被外部同步覆盖过三次，文件若被手改脏，
自动回灌等于把脏数据写进平台记忆。只在"文件有、豆包没有"时提示，等人点头再补。

**它们是文档层成员**：《个人偏好与点评.md》《用户画像.md》两份，
`search` 都能命中（标 `[文档]`），但都**不进卡数、不进 `匹配索引.json`**——
偏好和画像都不是经验卡，混进去会把 244 这个分母和"过期债"指标一起搞脏。

**设计文档也在文档层（v6.17 起）**：`架构与降权矩阵.md`、`目标态.md`、`长期路线.md`
是定论，搜到按普通文档处理；`对齐表.md`、`外部方法评估.md` 是 2026-11-12 的快照，
命中时会带 `[2026-11-12 快照]` 标记——**看见这个标记就别当现状引用**，数字随代码演进必然过期。
`说明_检索技能.md` **故意不登记**：它是本 SKILL.md 的长版副本，登记进去等于同一内容两个源，
改了一边忘另一边（D103 那类错）。

**体检报告也在文档层（v6.18 起）**：`体检报告.md` 是 2026-11-12 给这库自己拍的一次快照，
命中时带 `[2026-11-12 旧照片，数字已过期]`。保留它不是为了数字，是因为它是唯一一份
"当时怎么看待自己"的记录——诊断出的三个病（缺机制解释、失效条件空壳、使用率低）到
今天仍在，数字换了，病没换。**"体检"这个动作比那张单子值钱**：要看现在什么样，
跑 `stats` / `lint` / `activity` / `gate` 现取一遍，别翻旧照片。

## 工具边界（v6.44 起，砌墙不共享）

本工具只读写两处：
1. **自己的技能目录**（程序、`core/`）
2. **自己的库根** `$EXP_ROOT`（卡、三本账、`memory/`、`资产册/`）

**不读、不改其他技能群的任何目录。** 旧版 `mem` 会回退到 `memory-index` 技能的数据目录，那是别人的地盘，已拆除（2026-11-17）。
别的工具里也有同名 `core/recall.py`，那是它们的副本：本工具**不比对、不同步、不负责**。
`asset scan` 会读别的技能目录做目录清点——**只读**，是清点不是接管。

角色只有三种，见 `recall.py where`：**源（唯一可写）／投影（只由装命令覆盖）／僵尸（软链回源或删掉）**。

## 公地口径（共享，不是遗产）

这份库是**公地**：路径共享、数据共享。任何对话都能用，用完留痕。

1. **检索即翻**：`match` 命中的卡就是"被翻开的书"，不必等某个"主人"授权；
2. **用了就写回**：`use worked|failed|partial <卡> [一句话]` —— 这次到底用成没有，必须留痕；
3. **留痕三件套**：`使用台账.jsonl`（谁在什么问题上翻了哪张、结果如何）、`时效台账`（判据有没有跑通）、`发版流水`（改了什么、为什么）；
4. **不设"主"，看"活性"**：`activity` 报最常被翻的卡、待回写次数、一次没被翻过的张数；
5. **写回不是改卡**：回写只追加使用记录；改卡正文要另做，且不能删别人的卡（只能标 `superseded`）。

**"一次没被翻过"不是废，是还没轮到它。** 但**"被翻了却从不回写"是坏的**——那样的使用时序无法评估，等于每次都在盲翻。
